# 变更说明（2026-09-19）

版本：v1.2.8 → v1.2.9

对应上游 issue：[fineemb/lovelace-cn-map-card#24](https://github.com/fineemb/lovelace-cn-map-card/issues/24)

涉及文件：`cn-map-card.js`、`hacs.json`、`README.MD`、`dist/cn-map-card.js`

## 背景 / 原因

上游 issue #24 报告了三个相互独立、但都会导致"地图/标记点显示不正常"的问题。经核对，**这三个问题在 fork 的 master 上同样存在**（fork 基于更早的分支演进，v1.2.8 的部分防错代码未包含在内），此外还夹带了两处相关缺陷。

## 本次改了什么

### 问题 1：HACS 安装后卡片完全无法加载（sibling import 404）

| 位置 | 改动 | 原因 |
| --- | --- | --- |
| 模块头部 | 删除 `import './w3color.js'`，把 w3color.js 的能力实现整体内联进 `cn-map-card.js` | HACS 的 plugin 类型只支持在 `hacs.json` 里声明**单个** `filename`，不会一并下载同目录的 `w3color.js`；浏览器对该 sibling import 请求 404，整个 ES module 加载失败，卡片与编辑器都不渲染，控制台通常只有一条模块加载失败，没有高德相关报错 |
| `hacs.json` | 补回 `"content_in_root": true` 与 `"filename": "cn-map-card.js"` | fork 的 `hacs.json` 里这两项缺失。缺 `filename` 时 HACS 回退用仓库名 `lovelace-cn-map-card.js` 去 `dist/` 查找，该文件不存在，安装直接报错 |
| `dist/cn-map-card.js` | 由根目录文件同步覆盖 | 原先是残留的 v1.2.4 旧副本。一旦 HACS 回退到 `dist/` 布局（或用户手动从 `dist/` 取文件），装到的是 4 个版本之前的代码 |

内联时保留了 w3schools 的版权行，并删掉了卡片用不到的 `w3SetColorsByAttribute()`。卡片对 w3color 的唯一用途是 `_isDarkTheme()` 里的 `w3color(bg).lightness`。

### 问题 2：`setFitView` 竞态 —— 地图停在默认中心（北京）

`this.fit++` 曾经在 `_addMarker` 里同步执行，而真正把 marker 推进 `this.persons` 是在坐标转换的**异步回调** `_showMarker` 里。于是 `set hass()` 遍历结束后的同步判断会对着空的 `this.persons` 执行 `setFitView`（等同没执行），并把 `this.fit` 重置为 0；等回调真正返回时，再也不会进入该判断。

| 位置 | 改动 |
| --- | --- |
| 新增 `_settle()` / `_checkFit()` | 计数与自适应视野改为在**每个实体真正结算后**触发。`_settle()` 在每个实体上恰好调用一次（成功建点、坐标缺失、转换失败都算），不会卡在中间态 |
| `_addMarker` | 计数移出 `_showMarker`，改为 `_convertFrom` 回调里统一 `_settle()` |
| `_showMarker` | 删除 `this.fit++` 与 `if(this.fit === this.entities.length)this.loaded = true`（后者恒为死代码：`set hass` 在 `!this.loaded` 时已提前 return） |
| `set hass`、实体变更分支 | 补 `this.fit = 0`（否则实体变更后计数永远追不上 `entities.length`）、补 `this.persons = []`（`map.clearMap()` 已销毁旧 marker，仍留在数组里会让 `setFitView` 拿到已销毁对象）、补 `this.circle = {}` |
| `_checkFit()` | `setFitView` 前增加 `this.persons.length` 判断，实体全部无坐标时不再拿空数组调用 |

### 问题 3：`AMap.convertFrom` 对普通 Key 必然失败

`AMap.convertFrom` 内部请求高德"坐标转换"REST 接口，要求 Key 具备 **Web服务(REST API)** 平台权限；而地图渲染用的 Key 只能是 **Web端(JS API)** 平台，同一 Key 不能同时具备两个平台。因此对绝大多数用户，这个调用必然失败：REST 直连返回 `USERKEY_PLAT_NOMATCH`(10009)，JSAPI 内 JSONP 返回 `INVALID_USER_SCODE`(10008)。

| 位置 | 改动 |
| --- | --- |
| 新增 `_convertFrom(locations, type, callback)` | 统一坐标转换入口。配置了 `rest_key` 时直接 `fetch` REST 接口 `https://restapi.amap.com/v3/assistant/coordinate/convert`，不再依赖 `AMap.convertFrom`；**未配置 `rest_key` 时行为与旧版完全一致**，不影响现有用户 |
| 分批 | REST 坐标转换接口单次上限 40 个坐标点，历史轨迹可能上千点，按 40 分批并发请求后按序拼接 |
| `type: gaode` | 源数据本身已是 GCJ-02，直接短路返回、不转换。顺带修掉 `_updateMarker` 的既有 bug —— 它原先对 `gaode` 类型也会调用 `AMap.convertFrom(gps, 'gaode')`（非法 coordsys），导致该类实体的标记点永远不移动 |
| `_updateMarker` | 调用 `_gethistory(hours, entity, "", type)` 时 `type` 曾传空串，历史轨迹的坐标转换必然失败，改为传真实 `type` |
| 编辑器 | 新增 `rest_key` 输入项，并附一段说明为什么需要单独的 Key |

### 顺带修正的两处相关缺陷

| 位置 | 改动 | 原因 |
| --- | --- | --- |
| 模块头部 | 删除无条件执行的 `window._AMapSecurityConfig = { securityJsCode:'' }` | 该赋值在资源加载时执行，会覆盖用户在其它资源里配置的安全密钥，导致 2021-12 之后申请的 Key 地图加载失败。现改为仅在配置了 `securityJsCode` 时才写入，并同时传给 `AMapLoader.load` |
| `_loadMap` | 地图加载完成后立即 `this.hass = this._hass` 刷新一次 | 否则要等下一次 hass 推送才会进入加标记分支，安静环境下地图会长时间空白。此处 `catch` 也从 `console.log` 改为带说明的 `console.error` |

# 追加修复（v1.2.10）

## 现象

```
Uncaught TypeError: Cannot read properties of undefined (reading 'pn')
  x.prototype._getUserStyle = function(t) {
    t && (t = this.wmt(t),
      this.mapStyle.fn(t, this.Byt, function(t) { ...
        i.mapStyle.pn(function(t) { ... })
```

抛点在高德 JS API 内部，但根因在**配置侧**。

## 根因

`setMapStyle` 的入参是 `"amap://styles/" + style` 直接拼出来的，而 `style` 完全没有取值校验：

| 位置 | 配置 | 拼出的样式名 | 结果 |
| --- | --- | --- | --- |
| `_loadMap` | **未配置 `dark_mode`**（最常见） | `amap://styles/undefined` | 非法 |
| `_loadMap` / `set hass` | `dark_mode: true` | `amap://styles/true` | 非法 |
| `set hass` | `dark_mode: false` | 被 `\|\| "auto"` 吞成 `auto` | 与 README「`dark_mode: false` = 白天」不符 |

样式名非法时高德的样式加载失败，其内部 `mapStyle` 保持 `undefined`，紧接着 `_getUserStyle` 里
`i.mapStyle.pn(...)` 抛 `TypeError`。更严重的是这个异常会从 `set hass` 里冒出去，
**中断整条状态更新** —— 其后的主题判断、路况图层、标记点更新全部不再执行。

注意 `_loadMap` 是在 `connectedCallback` 里调用的：只要配置里没写 `dark_mode`，卡片首次连接就会撞上这条路径。

## 本次改了什么

| 位置 | 改动 |
| --- | --- |
| 新增模块级 `normalizeDarkMode(value)` | 取值归一化。`"auto"` 跟随主题；`true`/`"dark"` 夜间；`false`/`"normal"` 白天；高德内置样式名原样透传；控制台发布的自定义样式 ID 原样透传（也兼容直接粘贴 `amap://styles/xxx`）；其余（`undefined`/`null`/空串/数字/对象/含特殊字符/`"true"`/`"false"`）一律回退 `auto`。放在模块级是因为可视化编辑器也要用同一套规则 |
| 新增 `_applyMapStyle(style)` | 设置地图样式与 `#map` 的 `className` 的唯一出口。`setMapStyle` 外包 `try/catch`：高德抛错时回退 `normal` 并打 warn，不再让异常冒出去中断 `set hass` |
| 新增 `_resolveMapStyle()` | `auto` 时按当前主题解析为 `dark`/`normal` |
| 新增 `_updateMapStyle(hass)` | 从 `set hass` 抽出样式/主题更新逻辑 |
| `set hass` | `_updateMapStyle(hass)` 移到 `if(!this.loaded \|\| this.entities.length<1)return;` **之前**。原先 `entities` 为空时整条更新直接早退，`dark_mode: auto` 永远不跟随主题切换 |
| `_loadMap` | 改用 `normalizeDarkMode` + `_resolveMapStyle` + `_applyMapStyle`，不会再请求 `amap://styles/undefined`。此时 `_hass` 可能尚未注入，`auto` 先落 `normal`，等首次 hass 推送再按主题纠正 |
| `_themeVars` | 增加 `!hass \|\| !hass.themes` 守卫（`_resolveMapStyle` 会在 `_loadMap` 阶段被调用，此时 `_hass` 可能为 `undefined`） |
| 编辑器 | `darkMode` 改用 `normalizeDarkMode` 归一化后再比对单选按钮，`dark_mode: false` 现在正确显示为「白天模式」 |

## 未改动 / 待验证

- `cn-map-card.js` 与 `dist/cn-map-card.js` 已通过 `node --check`；桩环境用例扩到 13 组（新增 5 组覆盖本次崩溃路径）全部通过。
- 仍未在真实 HA 实例中验证 UI。请在目标版本确认：控制台首行为 `Version 1.2.10`；分别用「不写 `dark_mode`」「`dark_mode: true`」「`dark_mode: false`」「`dark_mode: auto`」四种配置打开卡片，均不应出现 `reading 'pn'`，且主题跟随正常。

# 追加修复（v1.2.11）

## 现象

「配置了人员后地图上没有显示」—— 底图正常渲染，但没有任何标记点。

## 根因（两条独立链路，都可能单独造成该现象）

### A. `_loadMap` 的异常级联：`loaded` 永远为 `false`

v1.2.10 之前，`_loadMap` 的 `.then()` 回调是这样的：

```js
AMapLoader.load(config).then(()=>{
  this.map = new AMap.Map(mapContainer, {...});          // 底图先渲染出来
  ...
  this.map.setMapStyle("amap://styles/"+style);          // ← dark_mode 未配置时在这里抛错
  this.trafficLayer = new AMap.TileLayer.Traffic({...});
  this.loaded = true;                                    // ← 永远执行不到
  if(this._hass && this._hass.states)this.hass = this._hass;
})
```

样式名非法导致 `setMapStyle` 抛 `reading 'pn'` → 回调中断 → `this.loaded` 保持 `false`。
而 `set hass` 的第一行就是 `if(!this.loaded || this.entities.length<1)return;` ——
于是 **底图能显示、标记点永远不添加**，且控制台除那条 TypeError 外没有别的线索。

这正是「地图显示了但没有人员标记点」最可能的原因，也是 v1.2.10 那条修复的连带效果：
只修样式名归一化还不够，必须保证加载后的增强步骤**不再能打断初始化流程**。

### B. 坐标转换失败被静默吞掉

v1.2.10 的 `_addMarker` 是这样一个静默分支：

```js
this._convertFrom(gps, type, function (err, result) {
  if (!err) that._showMarker(result, entity, color, type);   // 失败时什么都不做，也不打日志
  that._settle();
});
```

未配置 `rest_key` 且 Key 是纯 JS API 平台时，`AMap.convertFrom` 必然失败（见问题 3），
于是标记点被静默跳过 —— 用户只能看到一张空地图，无从判断是配置问题还是 Key 问题。

## 本次改了什么

| 位置 | 改动 |
| --- | --- |
| `_loadMap` | 把样式应用、路况图层初始化分别包进独立的 `try/catch`，**保证 `loaded = true` 一定执行**。任一增强步骤失败只告警，不影响标记点 |
| `_loadMap` | 地图就绪后打印一行体检信息（实体数、`key` / `securityJsCode` / `rest_key` 是否已配置），便于一眼确认配置状态 |
| `set hass` | 路况图层调用加 `if(this.trafficLayer)` 守卫（图层初始化失败时该字段可能不存在，否则会在标记点之后再次中断更新） |
| `connectedCallback` | 缺 `key` / `securityJsCode` 时前置明确报错（这两个是"地图能不能出来"的硬前提） |
| `_warnOnce(key,msg)` | 新增：同一条原因只提示一次。状态推送很频繁，不加节流会刷爆控制台 |
| `_addMarker` | 区分三种失败并各自告警：实体不存在 / 实体缺经纬度 / 坐标转换失败。原先全部静默返回 |
| `_convertFrom` | 无 `rest_key` 且 `AMap.convertFrom` 失败时，输出含**三种处置方案**的完整说明：① 配置 `rest_key`（推荐，精确）② 实体本身是高德坐标则改 `type: gaode` ③ 确实是 GPS 坐标又不想申请第二个 Key，可临时用 `gaode` 显示，代价是百米级偏移 |
| `_showMarker` | 调整顺序为**先创建标记点、再画精度圈**；精度圈半径非法（`radius` 与 `gps_accuracy` 都缺失）时直接跳过，并用 `try/catch` 隔离。此前半径非法可能让整段 `_showMarker` 抛错，连标记点一起丢掉 |
| `connectedCallback` | 补 `this.config = this.config || {}`，避免 `setConfig` 未调用时体检代码直接抛错 |

# 追加修复（v1.2.12）

## 现象

「配置了人员后，历史轨迹没有显示」——标记点正常，但看不到移动轨迹。

## 根因

### A. `datetime-local` 的取值格式非法（决定性）

```js
this.root.querySelector('#start_time').value = startTime.format("yyyy-MM-dd hh:mm")   // 空格分隔
```

`<input type="datetime-local">` 只接受 **`YYYY-MM-DDTHH:mm`**（`T` 分隔）。按 HTML 规范的
value sanitization 算法，非法字符串会被**置为空值**。于是：

```js
const startTime = new Date("");        // Invalid Date
startTime.toISOString()                // RangeError: Invalid time value
```

`_gethistory` 在发出请求之前就抛 `RangeError`，历史完全没有被查询 —— 轨迹自然不显示，
而且这个异常发生在 `_showMarker` 的调用链里，控制台往往只看到一条与轨迹无关的报错。

### B. `hours_to_show` 形同虚设

- `_loadMap` 里 `startTime.setHours(endTime.getHours() - hours_to_show)` 被注释掉，改成固定「今天 00:00」，
  所以 `hours_to_show` 配置**完全不起作用**。
- `_showMarker` 里又以 `hours_to_show > 0` 作为是否请求历史的前提。**不写这个选项的用户，
  永远不会请求历史轨迹**。两条合起来：配了没效果，不配又完全没有。

### C. 空结果与失败全静默

```js
.then(function(res) {
  let arr = controlArrayLength(res[0])   // res 为 [] 时 res[0] 是 undefined -> TypeError
  ...
})                                        // 且没有 .catch
```

无历史数据时抛 `TypeError`，成为未处理的 Promise 拒绝，控制台没有任何可读线索。

### D. 轨迹刷新时圆点不更新、颜色可能为空

- 更新已有轨迹时只调用 `setPath`，停留点圆点仍停在旧位置。
- `_updateMarker` 调用 `_gethistory(hours, entity, "", type)` 传空颜色，`strokeColor: ""` 画出的线不可见。

### E. 分批转换并发过高

1000 点轨迹按 40 点分批后，`Promise.all` 会**同时**打出 25 个请求，极易触发高德 QPS 限制
（`CUQPS_HAS_EXCEEDED_THE_LIMIT`），整条轨迹失败。

## 本次改了什么

| 位置 | 改动 |
| --- | --- |
| 新增 `formatLocalInput(d)` | 按 `YYYY-MM-DDTHH:mm` 写入时间控件，替换 `startTime.format("yyyy-MM-dd hh:mm")` |
| 新增 `parseLocalInput(value)` | 显式按本地时间解析（兼容 `T` 与空格分隔），非法返回 `null`，不再出现 Invalid Date / RangeError |
| 删除 `Date.prototype.format` | 该 monkey-patch 只被上面两处使用，却会污染全局 `Date` 原型、与其它卡片冲突 |
| 新增 `_historyWindow()` | 优先用底部时间控件；控件为空/非法/顺序颠倒时回退：`hours_to_show > 0 → [now-hours, now]`，否则 `[今天 00:00, now]` |
| `_loadMap` | 恢复 `hours_to_show` 的语义，用它初始化默认窗口（此前该行被注释，配置无效） |
| `_showMarker` | 去掉 `hours_to_show > 0` 门槛，`person` / `device_tracker` 一律请求轨迹 |
| `_gethistory` | 重写：空结果保护 + `.catch` 诊断；`arr` 用索引遍历并跳过无坐标记录；日志区分 info（正常空结果）与 warn（数据/接口异常） |
| 新增 `_drawTrail()` | 统一原来 `gaode` / 非 `gaode` 两份重复实现；更新轨迹时**先移除旧圆点再重建**，避免位置错乱与对象泄漏 |

# 追加修复（v1.2.13）

## 现象

「人员的历史轨迹又没有显示了」。标记点正常，轨迹缺失；且重启/刷新后可能恢复，切换视图后再次消失。

## 根因

### A. 生命周期：detach 后未销毁地图与派生状态（"又"的来源）

`connectedCallback` 每次都会执行 `_loadMap()`，即 **new 一个 AMap.Map**；但 `disconnectedCallback`
只做了 `_resizeObserver.disconnect()`：

```js
disconnectedCallback(){
  if (this._resizeObserver) this._resizeObserver.disconnect();   // 只断开了 resize 监听
}
```

于是切换视图 / 进出编辑模式后：

1. 旧地图实例被丢弃（没有 `destroy()`，还泄漏）；
2. `this.markers` / `this.paths` / `this.historyPath` / `this.loaded` 全部**残留**，仍指向旧地图上的对象；
3. 重新连接时 `_loadMap` 建了新地图，末尾 `this.hass = this._hass` 走 `set hass`；
4. 因为 `oldentities === entities`（没变），进入 `_updateMarker` 分支；而 `positions` 未变、距离为 0，
   什么都不会重画 —— 新地图上既没有 marker 也没有 polyline，`_retryTrails` 又因为 `paths[entity]`
   仍然存在而跳过。

结论：**切换视图后，标记点与轨迹一起消失，直到刷新页面**。这解释了"上次好了，这次又没了"。

### B. 一次失败被永久锁死

```js
if(that.historyPath[entity] == arr.length)return;
that.historyPath[entity] = arr.length;        // ← 在坐标转换之前就写入
...
that._convertFrom(lineArr, type, function(err, locations){
  if(err)return;                              // 失败：但 historyPath 已经被标记为"N 点"
  draw(locations);
});
```

转换失败后，下一次同点数的请求会被开头的去重直接挡掉。而 `_gethistory` 只在**建立标记点**时调用一次
（非追踪模式），所以一次瞬时失败（HA 启动中、高德 QPS、网络抖动）就意味着这条轨迹再也不会出现。

### C. 停留时长非法导致整段绘制中断

`getRadius()` 在 `last_updated` 无法解析时返回 `[NaN, "NaN秒"]`，`radius: NaN` 传给
`AMap.CircleMarker` 可能抛错。虽然折线已在之前创建，但异常会冒到 `_convertFrom` 的 `.catch`，
被误报成「REST 坐标转换失败」，掩盖真实原因。

### D. 无收益且可能失效的查询参数

请求里带着 `significant_changes_only=0`。该参数默认即为 false（返回全部状态变化），显式传递没有收益；
且它在不同 HA 版本中的存废不一致，存在请求被拒的风险。

## 本次改了什么

| 位置 | 改动 |
| --- | --- |
| `disconnectedCallback` | 补 `map.destroy()`、`map = null`、`loaded = false`，并清空 `markers / paths / circle / historyPath / _trailRetry / persons / positions / oldentities / fit`。保证重新连接时完整重建（同时修掉旧地图实例泄漏） |
| 新增 `_retryTrails()` | 在 `set hass` 的"仅更新位置"分支里调用。对缺少轨迹的 `person` / `device_tracker` 做有限重试：最多 3 次，间隔 30/60/90 秒；`paths[entity]` 存在即停止。瞬时失败不再需要刷新页面 |
| `_gethistory` | `historyPath` 改为**绘制成功后**写入；成功后清理该实体的重试计数并输出一条 info（记录条数 / 有效坐标数 / 时间窗口） |
| `_gethistory` | `draw()` 包 `try/catch`，AMap 绘制异常不再冒到坐标转换的 catch 里被误报 |
| `_gethistory` | 移除 `significant_changes_only=0` |
| `_drawTrail` | 停留点半径做 `isFinite` 兜底（非法则用 4），避免 NaN 打断绘制 |
| `set hass` / 构造函数 | 新增 `_trailRetry` 状态，并在实体变更时重置 |
